# Security

Security trong Kubernetes nên hiểu theo mô hình **defense-in-depth**: không có một cấu hình duy nhất làm cluster “an toàn”, mà phải bảo vệ nhiều lớp cùng lúc: **API server, identity, RBAC, admission control, Pod, network, Secret, node, image supply chain và audit/logging**. Kubernetes chính thức mô tả security là tập hợp nhiều API, cơ chế kiểm soát và policy; trong đó bảo vệ control plane, kiểm soát truy cập API, TLS in-transit và encryption at-rest là các phần rất quan trọng.

## Bức tranh tổng quát

Một request vào Kubernetes thường đi theo luồng:

```
User / CI/CD / Pod
        |
        v
kube-apiserver
        |
        |-- Authentication: bạn là ai?
        |-- Authorization: bạn được phép làm gì?
        |-- Admission Control: object này có được tạo/sửa/xóa không?
        |
        v
etcd
```

Điểm cần nhớ: **kube-apiserver là cửa chính của Kubernetes**. Hầu hết thao tác như tạo Pod, sửa Deployment, đọc Secret, tạo Service, update ConfigMap đều đi qua API server. Vì vậy, bảo mật Kubernetes bắt đầu từ việc kiểm soát chặt ai được gọi API và gọi với quyền gì.

## Authentication — xác thực danh tính

**Authentication** trả lời câu hỏi: “Request này đến từ ai?”

Kubernetes có hai nhóm identity chính:

| Loại identity | Ý nghĩa |
| --- | --- |
| Normal user | Người dùng thật, thường đến từ hệ thống bên ngoài như certificate, OIDC, IAM, SSO. Kubernetes không có object `User` nội bộ để tạo user bằng API. |
| ServiceAccount | Identity dành cho workload chạy trong Pod. Đây là object do Kubernetes quản lý. |

Theo tài liệu Kubernetes, normal user không được thêm trực tiếp qua API Kubernetes, còn ServiceAccount là user do Kubernetes quản lý, gắn với namespace và thường được dùng để Pod gọi Kubernetes API.

Ví dụ: một Pod cần list ConfigMap trong namespace thì Pod đó không nên dùng quyền admin. Nó nên dùng một `ServiceAccount` riêng, sau đó gán RBAC tối thiểu cho ServiceAccount đó.

```
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-reader
  namespace: demo
automountServiceAccountToken: false
```

`automountServiceAccountToken: false` nghĩa là Pod sẽ không tự động mount token Kubernetes API nếu workload không cần gọi API. Kubernetes cũng khuyến nghị tránh dùng `default` ServiceAccount và chỉ bật auto-mount token khi Pod thật sự cần truy cập API.

## Authorization — phân quyền

**Authorization** trả lời câu hỏi: “Identity này được phép làm gì?”

Kubernetes hỗ trợ nhiều authorization mode như RBAC, ABAC, Webhook. Nếu nhiều authorizer cùng được cấu hình, request được cho phép nếu có ít nhất một authorizer cho phép; nếu tất cả từ chối thì request bị trả về `403 Forbidden`.

Cơ chế phổ biến nhất là **RBAC — Role-Based Access Control**. RBAC dùng API group `rbac.authorization.k8s.io` để định nghĩa policy truy cập trong Kubernetes.

Các object chính của RBAC:

| Object | Phạm vi | Vai trò |
| --- | --- | --- |
| `Role` | Namespace | Định nghĩa quyền trong một namespace |
| `ClusterRole` | Cluster-wide | Định nghĩa quyền toàn cluster hoặc quyền có thể tái sử dụng |
| `RoleBinding` | Namespace | Gán `Role` hoặc `ClusterRole` cho user/group/ServiceAccount trong namespace |
| `ClusterRoleBinding` | Cluster-wide | Gán `ClusterRole` trên toàn cluster |

Ví dụ RBAC tối thiểu cho Pod chỉ được đọc ConfigMap:

```
apiVersion: v1
kind: ServiceAccount
metadata:
  name: config-reader
  namespace: demo
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: read-configmaps
  namespace: demo
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get","list","watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: bind-config-reader
  namespace: demo
subjects:
  - kind: ServiceAccount
    name: config-reader
    namespace: demo
roleRef:
  kind: Role
  name: read-configmaps
  apiGroup: rbac.authorization.k8s.io
```

Nguyên tắc quan trọng nhất của RBAC là **least privilege**: chỉ cấp đúng quyền cần thiết. Kubernetes khuyến nghị ưu tiên `RoleBinding` ở namespace thay vì `ClusterRoleBinding`, tránh wildcard permission như `*`, tránh dùng `cluster-admin` khi không cần, và tránh thêm user vào group `system:masters` vì group này có quyền superuser không bị RBAC giới hạn.

Một điểm rất dễ bị bỏ qua: quyền **tạo Pod/Deployment** trong namespace có thể gián tiếp dẫn đến quyền đọc Secret, ConfigMap, mount volume hoặc sử dụng ServiceAccount trong namespace đó. Vì vậy, không nên nghĩ rằng “chỉ cho tạo Pod” là quyền thấp.

## Admission Control — kiểm soát trước khi object được lưu

Sau authentication và authorization, request đi qua **Admission Control**.

Admission controller là đoạn logic trong API server, chặn request trước khi object được lưu lại, nhưng sau khi request đã được xác thực và phân quyền. Admission controller áp dụng cho request tạo, sửa, xóa object; nó không chặn request đọc như `get`, `list`, `watch`.

Có hai nhóm chính:

| Loại | Tác dụng |
| --- | --- |
| Mutating admission | Có thể sửa object trước khi lưu |
| Validating admission | Chỉ kiểm tra và cho phép hoặc từ chối |

Ví dụ admission policy có thể chặn:

- Container chạy privileged.
- Image dùng tag `latest`.
- Pod không có `runAsNonRoot`.
- Deployment thiếu resource requests/limits.
- Namespace không đạt Pod Security Standard.

Kubernetes có `ValidatingAdmissionPolicy` dùng CEL để kiểm tra cấu hình, ví dụ có thể dùng để cấm image tag `latest`.

## Pod Security Standards và Pod Security Admission

Đây là phần rất quan trọng khi bảo mật workload.

Kubernetes định nghĩa **Pod Security Standards** với ba mức:

| Mức | Ý nghĩa |
| --- | --- |
| `privileged` | Gần như không hạn chế, cho phép quyền rất rộng, phù hợp workload hệ thống đặc biệt |
| `baseline` | Chặn các cấu hình dễ leo thang đặc quyền, nhưng vẫn tương thích nhiều workload phổ biến |
| `restricted` | Mức chặt nhất, theo các best practices hardening hiện tại |

Ba mức này đi từ dễ dãi đến nghiêm ngặt, và `restricted` là mức nên hướng đến cho workload application thông thường nếu có thể.

Kubernetes hiện đại không còn dùng `PodSecurityPolicy` nữa. `PodSecurityPolicy` đã deprecated từ Kubernetes v1.21 và bị remove từ v1.25; thay vào đó nên dùng **Pod Security Admission** hoặc admission plugin bên thứ ba.

Ví dụ enforce mức `restricted` cho namespace:

```
kubectl label namespace production \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/warn=restricted
```

Ý nghĩa:

| Mode | Hành vi |
| --- | --- |
| `enforce` | Vi phạm policy thì reject Pod |
| `audit` | Cho phép nhưng ghi audit annotation |
| `warn` | Cho phép nhưng cảnh báo người dùng |

Pod Security Admission áp dụng các restriction ở cấp namespace khi Pod được tạo.

## SecurityContext — hardening Pod và container

`securityContext` dùng để cấu hình privilege và access control cho Pod hoặc container. Nó có thể kiểm soát UID/GID, SELinux, privileged/unprivileged mode, Linux capabilities, AppArmor, seccomp, `allowPrivilegeEscalation`, `readOnlyRootFilesystem`, v.v.

Một cấu hình container tương đối an toàn nên có các ý tưởng sau:

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: secure-app
  namespace: demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: secure-app
  template:
    metadata:
      labels:
        app: secure-app
    spec:
      serviceAccountName: app-reader
      automountServiceAccountToken: false

      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
        fsGroup: 10001
        seccompProfile:
          type: RuntimeDefault

      containers:
        - name: app
          image: registry.example.com/secure-app@sha256:xxxxxxxx
          ports:
            - containerPort: 8080

          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            privileged: false
            capabilities:
              drop:
                - ALL

          resources:
            requests:
              cpu:"100m"
              memory:"128Mi"
            limits:
              memory:"256Mi"
```

Ý nghĩa của cấu hình trên:

| Cấu hình | Tác dụng |
| --- | --- |
| `runAsNonRoot: true` | Không chạy process chính bằng root |
| `runAsUser`, `runAsGroup` | Chạy bằng UID/GID ít đặc quyền |
| `allowPrivilegeEscalation: false` | Không cho process tăng đặc quyền |
| `readOnlyRootFilesystem: true` | Root filesystem của container ở chế độ read-only |
| `capabilities.drop: ["ALL"]` | Bỏ toàn bộ Linux capabilities mặc định |
| `seccompProfile: RuntimeDefault` | Dùng seccomp profile mặc định của runtime |
| `privileged: false` | Không chạy container privileged |

Kubernetes Application Security Checklist cũng khuyến nghị chạy non-root, tắt privilege escalation, dùng read-only root filesystem, tránh privileged container, drop capabilities và chỉ thêm lại capability thật sự cần thiết.

## Network Security và NetworkPolicy

Mặc định, nếu không có NetworkPolicy, Pod thường ở trạng thái **non-isolated**: outbound được phép, inbound cũng được phép. NetworkPolicy dùng để quy định Pod nào được nhận traffic từ đâu và được gửi traffic đến đâu.

Điểm cực kỳ quan trọng: NetworkPolicy chỉ có tác dụng nếu CNI/network plugin hỗ trợ NetworkPolicy. Nếu cluster dùng plugin không enforce NetworkPolicy, bạn tạo YAML NetworkPolicy thì cũng không có tác dụng bảo mật thực tế.

Ví dụ default deny toàn bộ ingress và egress trong namespace:

```
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: demo
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
```

Sau đó mở đúng traffic cần thiết, ví dụ chỉ cho `frontend` gọi `backend` port `8080`:

```
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: demo
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080
```

Nếu đã default deny egress, thường cần mở DNS để Pod resolve service name:

```
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: demo
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
```

NetworkPolicy là additive, tức là nhiều policy cùng áp dụng thì quyền được phép là hợp của các rule cho phép. Với kết nối Pod-to-Pod, egress ở phía nguồn và ingress ở phía đích đều cần cho phép thì traffic mới đi được.

## Secret Security

`Secret` là object dùng để chứa dữ liệu nhạy cảm nhỏ như password, token hoặc key. Dùng Secret giúp tránh hardcode credential trực tiếp vào image hoặc manifest Pod.

Nhưng Secret không tự động đồng nghĩa với “đã mã hóa an toàn”. Theo tài liệu Kubernetes, Secret mặc định được lưu **không mã hóa** trong backing store của API server, tức là etcd; ai có quyền API đọc Secret hoặc quyền truy cập etcd đều có thể đọc hoặc sửa Secret. Kubernetes khuyến nghị bật encryption at rest, cấu hình RBAC least privilege cho Secret, giới hạn container được dùng Secret, và cân nhắc external Secret store provider.

Các nguyên tắc thực tế:

| Việc nên làm | Lý do |
| --- | --- |
| Bật encryption at rest cho Secret | Tránh Secret nằm plaintext trong etcd |
| Không cấp quyền `get/list/watch secrets` rộng rãi | Đọc Secret gần tương đương lấy credential |
| Tách namespace theo mức độ tin cậy | Người có quyền tạo Pod trong namespace có thể gián tiếp dùng Secret |
| Không commit Secret manifest plaintext lên Git | Git history rất khó xóa sạch |
| Dùng external secret manager khi phù hợp | Ví dụ cloud secret manager hoặc CSI Secret Store |

Kubernetes hỗ trợ encryption at rest cho persistent API resource data, bao gồm Secret. Nếu không cấu hình `--encryption-provider-config`, API server sẽ lưu plain-text representation vào etcd, tức chưa bật encryption at rest.

Với cluster production, nên cân nhắc KMS provider. Trong Kubernetes 1.36, Kubernetes khuyến nghị dùng **KMS v2** nếu khả thi; KMS v1 đã deprecated từ v1.28 và bị disabled mặc định từ v1.29.

## Node và Kubelet Security

Node là nơi container thật sự chạy, nên nếu attacker chiếm được node thì có thể ảnh hưởng nhiều workload trên node đó.

Một điểm cần chú ý là **kubelet HTTPS endpoint**. Tài liệu Kubernetes nói kubelet endpoint có API cho phép truy cập dữ liệu nhạy cảm và thực hiện các thao tác mạnh trên node/container. Vì vậy cần cấu hình authentication và authorization cho kubelet cẩn thận.

Các điểm hardening quan trọng:

| Khu vực | Khuyến nghị |
| --- | --- |
| Kubelet anonymous access | Tắt bằng `--anonymous-auth=false` |
| Kubelet authorization | Dùng `--authorization-mode=Webhook` thay vì mặc định quá rộng |
| Node access | Hạn chế SSH vào node, chỉ admin cần thiết mới có quyền |
| Privileged workload | Không chạy privileged Pod trừ khi thật sự cần |
| DaemonSet hệ thống | Review kỹ vì chạy trên nhiều node, blast radius lớn |
| Runtime/OS | Patch thường xuyên, dùng container runtime được support |

Đặc biệt, quyền `nodes/proxy` rất nguy hiểm: Kubernetes cảnh báo quyền này có thể cấp quyền truy cập các kubelet API, bao gồm API có thể execute command trong container trên node.

## Image Security và Supply Chain

Kubernetes không chỉ cần bảo vệ runtime, mà còn phải bảo vệ thứ được deploy vào cluster.

Các khuyến nghị nền tảng:

| Kiểm soát | Ý nghĩa |
| --- | --- |
| Scan image trước khi deploy | Phát hiện vulnerability trong base image, package, binary |
| Ký và xác minh image | Giảm rủi ro deploy image giả mạo |
| Tránh dùng tag `latest` | Khó kiểm soát chính xác version đang chạy |
| Ưu tiên image digest | Digest gắn với nội dung cụ thể của image |
| Dùng private registry có kiểm soát | Giảm rủi ro kéo image không tin cậy |
| Dùng admission policy | Chặn image không đạt chuẩn trước khi vào cluster |

Kubernetes Application Security Checklist khuyến nghị scan image trước khi deploy và dùng container signing để xác thực chữ ký image trước khi triển khai vào cluster.

## Audit Logging

Audit giúp trả lời các câu hỏi: ai đã làm gì, khi nào, với object nào, từ đâu, và kết quả ra sao.

Kubernetes auditing tạo bản ghi có liên quan đến security theo trình tự thời gian cho hoạt động của user, application dùng Kubernetes API và chính control plane. Audit event được sinh ra trong kube-apiserver, xử lý theo audit policy và ghi ra backend như log file hoặc webhook.

Nên audit các hành động nhạy cảm như:

- Đọc hoặc thay đổi Secret.
- Tạo/sửa Role, ClusterRole, RoleBinding, ClusterRoleBinding.
- Tạo Pod privileged.
- Sửa namespace label liên quan Pod Security Admission.
- Exec vào Pod.
- Port-forward.
- Tạo ValidatingWebhook/MutatingWebhook.
- Thay đổi admission policy.

Ví dụ các command nên thường xuyên kiểm tra:

```
kubectlget clusterrolebinding
kubectlget rolebinding-A
kubectlget pods-A-o wide
kubectlget networkpolicy-A
kubectlget secrets-A
kubectl auth can-i--list
```

## Checklist học và triển khai Security trong Kubernetes

Bảng sau là checklist dễ nhớ:

| Lớp bảo mật | Câu hỏi cần tự kiểm tra |
| --- | --- |
| API Server | Có TLS không? Có bật audit không? Có giới hạn endpoint public không? |
| Authentication | User đến từ nguồn tin cậy chưa? ServiceAccount có tách theo workload không? |
| RBAC | Có dùng least privilege không? Có tránh wildcard, `cluster-admin`, `system:masters` không? |
| Admission | Có enforce Pod Security Standards không? Có chặn image/pod config nguy hiểm không? |
| Pod Security | Pod có chạy non-root không? Có tắt privilege escalation không? Có drop capabilities không? |
| Network | Có default deny không? Có chỉ mở traffic cần thiết không? CNI có enforce NetworkPolicy không? |
| Secret | Secret có encryption at rest không? RBAC đọc Secret có bị cấp quá rộng không? |
| Node | Kubelet có tắt anonymous auth không? Node có bị SSH rộng rãi không? |
| Image | Image có scan/ký/pin digest không? Có tránh `latest` không? |
| Audit | Có log hành động nhạy cảm không? Có cảnh báo khi RBAC/Secret/Pod security thay đổi không? |
