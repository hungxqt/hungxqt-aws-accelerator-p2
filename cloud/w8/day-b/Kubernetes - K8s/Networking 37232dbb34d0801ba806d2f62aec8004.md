# Networking

Networking trong Kubernetes là toàn bộ cơ chế giúp **Pod, Service, Node và người dùng bên ngoài cluster giao tiếp với nhau**. Có thể hiểu Kubernetes networking xoay quanh 4 bài toán chính:

1. Container trong cùng một Pod giao tiếp với nhau như thế nào?
2. Pod này gọi Pod khác như thế nào?
3. Pod gọi một nhóm Pod ổn định thông qua Service như thế nào?
4. Người dùng bên ngoài truy cập ứng dụng trong cluster như thế nào?

## Mô hình mạng nền tảng của Kubernetes

Kubernetes dùng mô hình mạng khá “phẳng”:

```
Pod A ---- gọi trực tiếp ---- Pod B
Pod C ---- gọi trực tiếp ---- Pod D
```

Mỗi Pod trong cluster có **một IP riêng, duy nhất trong toàn cluster**. Các container bên trong cùng một Pod chia sẻ cùng network namespace, nên có thể gọi nhau qua `localhost`. Theo mô hình mặc định, các Pod có thể giao tiếp trực tiếp với nhau, kể cả khi chúng nằm trên các Node khác nhau, miễn là không bị chặn bởi NetworkPolicy hoặc cấu hình mạng riêng.

Ví dụ:

```
Pod frontend: 10.244.1.10
Pod backend:  10.244.2.20

frontend có thể gọi backend qua:
http://10.244.2.20:8080
```

Tuy nhiên, trong thực tế **không nên hard-code Pod IP**, vì Pod có thể bị xóa, tạo lại, scale up, scale down và đổi IP bất cứ lúc nào.

## Pod networking

Pod là đơn vị nhỏ nhất để chạy workload trong Kubernetes. Một Pod có thể chứa một hoặc nhiều container. Các container trong cùng Pod được co-locate, co-schedule và chia sẻ tài nguyên mạng. Vì vậy, nếu container A và container B nằm trong cùng Pod, chúng có thể giao tiếp qua `localhost`.

Ví dụ:

```
Pod payment
├── app container       lắng nghe port 8080
└── sidecar container  gọi http://localhost:8080
```

Điểm quan trọng:

```
Cùng Pod      → gọi qua localhost
Khác Pod      → gọi qua Pod IP hoặc Service
Khác Node     → vẫn phải gọi được qua Pod IP nếu network plugin hỗ trợ đúng mô hình Kubernetes
```

## CNI / Network Plugin

Kubernetes không tự mình triển khai toàn bộ network data plane. Nó định nghĩa **mô hình mạng**, còn việc cấp IP cho Pod, route traffic giữa Node, overlay network, policy enforcement… thường do **network plugin** đảm nhiệm.

Ví dụ các network plugin phổ biến:

```
Calico
Cilium
Flannel
Weave Net
Antrea
```

Network plugin thường chịu trách nhiệm:

- Cấp IP cho Pod
- Tạo route giữa các Node
- Đảm bảo Pod-to-Pod communication
- Hỗ trợ hoặc không hỗ trợ NetworkPolicy
- Có thể dùng overlay như VXLAN hoặc routing trực tiếp tùy plugin

Đây là lý do khi bạn tạo cluster bằng kubeadm, bạn thường phải cài thêm một network plugin. Nếu không, Pod có thể không giao tiếp được với nhau.

## Service networking

Vấn đề lớn là **Pod không ổn định**. Một Deployment có thể tạo, xóa, thay thế Pod liên tục. Vì vậy Kubernetes cung cấp **Service** để tạo một endpoint ổn định phía trước các Pod.

Kubernetes Service là abstraction dùng để expose một ứng dụng đang chạy trên một hoặc nhiều Pod. Service định nghĩa một tập backend logic, thường được chọn bằng label selector, và cung cấp cách truy cập ổn định vào tập Pod đó.

Ví dụ:

```
apiVersion: v1
kind: Service
metadata:
  name: backend-service
spec:
  selector:
    app: backend
  ports:
    - port: 80
      targetPort: 8080
```

Nếu có 3 Pod backend:

```
backend-pod-1: 10.244.1.11:8080
backend-pod-2: 10.244.1.12:8080
backend-pod-3: 10.244.2.13:8080
```

Service sẽ cung cấp một địa chỉ ổn định:

```
backend-service:80
```

Client chỉ cần gọi:

```
http://backend-service
```

Kubernetes sẽ route traffic đến một trong các Pod backend phù hợp.

## Các loại Service quan trọng

### ClusterIP

Đây là loại Service mặc định. Nó chỉ expose ứng dụng **bên trong cluster**.

```
spec:
  type: ClusterIP
```

Dùng khi:

```
frontend gọi backend
backend gọi database nội bộ
microservice này gọi microservice khác
```

Ví dụ:

```
frontend Pod → backend-service.default.svc.cluster.local
```

### NodePort

NodePort expose Service qua một port trên mỗi Node.

```
spec:
  type: NodePort
```

Ví dụ:

```
Node IP: 192.168.1.10
NodePort: 30080

Client gọi:
http://192.168.1.10:30080
```

Dùng để test hoặc expose đơn giản, nhưng trong production thường không phải lựa chọn tốt nhất nếu dùng cloud load balancer hoặc ingress controller.

### LoadBalancer

LoadBalancer dùng khi cluster chạy trên cloud provider hỗ trợ load balancer.

```
spec:
  type: LoadBalancer
```

Khi tạo Service loại này, cloud provider có thể tạo external load balancer để forward traffic vào Service. Đây là cách phổ biến để expose ứng dụng ra Internet trong môi trường cloud.

### ExternalName

ExternalName không proxy traffic đến Pod. Nó ánh xạ Service name trong Kubernetes sang một DNS name bên ngoài.

Ví dụ:

```
apiVersion: v1
kind: Service
metadata:
  name: external-db
spec:
  type: ExternalName
  externalName: db.example.com
```

Khi Pod gọi:

```
external-db.default.svc.cluster.local
```

DNS sẽ trỏ đến:

```
db.example.com
```

ExternalName hữu ích khi bạn muốn ứng dụng trong Kubernetes gọi một dịch vụ nằm ngoài cluster bằng tên nội bộ dễ quản lý.

## EndpointSlice

Service không trực tiếp “biết” Pod nào đang chạy. Kubernetes dùng **EndpointSlice** để theo dõi các backend endpoint phía sau Service.

Ví dụ:

```
Service: backend-service
EndpointSlices:
  - 10.244.1.11:8080
  - 10.244.1.12:8080
  - 10.244.2.13:8080
```

Khi Pod scale up hoặc bị xóa, Kubernetes cập nhật EndpointSlice tương ứng. Kubernetes hiện khuyến nghị dùng EndpointSlice thay cho Endpoints cũ vì EndpointSlice mở rộng tốt hơn và hỗ trợ các tính năng mới hơn.

## kube-proxy

`kube-proxy` chạy trên mỗi Node. Nó quan sát Service trong Kubernetes API và cấu hình forwarding rule trên Node để traffic đến Service có thể được chuyển đến backend Pod phù hợp. Theo tài liệu Kubernetes, kube-proxy có thể thực hiện forwarding TCP, UDP, SCTP hoặc round-robin đến tập backend.

Luồng đơn giản:

```
Pod frontend
   |
   | gọi backend-service:80
   v
Service virtual IP
   |
   | kube-proxy rule
   v
Một backend Pod thật
```

Nói dễ hiểu:

```
Service = địa chỉ ổn định
EndpointSlice = danh sách backend thật
kube-proxy = cơ chế chuyển traffic từ Service đến backend
```

## DNS trong Kubernetes

Kubernetes tạo DNS record cho Service và Pod, giúp workload gọi nhau bằng tên thay vì IP. Kubelet cấu hình DNS cho Pod để container có thể lookup Service name.

Ví dụ có Service:

```
backend-service
namespace: default
```

Pod trong cùng namespace có thể gọi:

```
http://backend-service
```

Pod ở namespace khác nên gọi đầy đủ hơn:

```
http://backend-service.default.svc.cluster.local
```

Cấu trúc DNS thường là:

```
<service-name>.<namespace>.svc.cluster.local
```

Ví dụ:

```
payment-service.prod.svc.cluster.local
```

Trong thực tế, DNS là cách gọi Service phổ biến nhất trong Kubernetes.

## Ingress

Service `LoadBalancer` có thể expose từng app ra ngoài, nhưng nếu bạn có nhiều ứng dụng HTTP/HTTPS thì dùng nhiều LoadBalancer sẽ tốn kém và khó quản lý.

Ingress giải quyết bài toán này bằng cách định nghĩa rule HTTP/HTTPS để route traffic từ bên ngoài vào Service trong cluster. Ingress có thể hỗ trợ load balancing, SSL termination và name-based virtual hosting.

Ví dụ:

```
https://example.com/api   → api-service
https://example.com/web   → web-service
```

Manifest ví dụ:

```
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
spec:
  rules:
    - host: example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 80
```

Lưu ý quan trọng: Ingress resource chỉ là cấu hình. Để nó hoạt động, cluster cần có **Ingress Controller**, ví dụ NGINX Ingress Controller, Traefik, HAProxy, Kong, Istio Ingress, Cilium Ingress… Kubernetes cũng ghi chú rằng Ingress API đã “frozen” và khuyến nghị dùng Gateway API cho các nhu cầu mới, phức tạp hơn.

## Gateway API

Gateway API là hướng mới hơn để quản lý traffic vào cluster. Nó cung cấp các API mở rộng hơn Ingress, hỗ trợ mô hình phân vai rõ hơn và các routing case phức tạp hơn như header-based matching, traffic weighting, HTTPRoute, GRPCRoute.

So sánh nhanh:

```
Service       → expose Pod ở mức L4 cơ bản
Ingress       → route HTTP/HTTPS vào Service
Gateway API   → mô hình routing hiện đại, mở rộng hơn Ingress
```

Nếu mới học Kubernetes, nên học theo thứ tự:

```
Service → Ingress → Gateway API
```

## NetworkPolicy

Mặc định, nếu network plugin cho phép, các Pod có thể giao tiếp với nhau khá tự do. Để kiểm soát traffic, Kubernetes cung cấp **NetworkPolicy**.

NetworkPolicy dùng để quy định traffic nào được phép đi vào hoặc đi ra khỏi một nhóm Pod. Policy có thể dựa trên Pod selector, namespace selector hoặc IP block.

Ví dụ: chỉ cho Pod có label `app: frontend` gọi vào Pod backend port 8080.

```
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080
```

Điểm cực kỳ quan trọng: NetworkPolicy chỉ có hiệu lực nếu network plugin hỗ trợ NetworkPolicy. Nếu bạn tạo NetworkPolicy nhưng plugin không implement nó, policy sẽ không có tác dụng.

## Các luồng traffic thường gặp

### Luồng 1: Container trong cùng Pod

```
container A → localhost → container B
```

Dùng khi app container cần sidecar container, ví dụ logging sidecar, proxy sidecar.

### Luồng 2: Pod gọi Pod trực tiếp

```
pod-a-ip → pod-b-ip
```

Về mặt kỹ thuật có thể làm được, nhưng không nên phụ thuộc vào Pod IP vì Pod dễ bị thay thế.

### Luồng 3: Pod gọi Service nội bộ

```
frontend Pod → backend-service → backend Pods
```

Đây là cách phổ biến nhất cho microservices trong cluster.

### Luồng 4: User bên ngoài gọi app qua LoadBalancer

```
User → Cloud Load Balancer → Service LoadBalancer → Pod
```

Dễ dùng, phù hợp khi bạn expose một service chính ra ngoài.

### Luồng 5: User bên ngoài gọi app qua Ingress

```
User → Ingress Controller → Ingress rule → Service → Pod
```

Phù hợp khi có nhiều route HTTP/HTTPS, nhiều domain, nhiều path.

## Tóm tắt dễ nhớ

```
Pod IP
→ IP thật của từng Pod, không ổn định lâu dài.

Service
→ địa chỉ ổn định để truy cập một nhóm Pod.

ClusterIP
→ Service nội bộ trong cluster.

NodePort
→ expose Service qua port trên Node.

LoadBalancer
→ expose Service ra ngoài bằng cloud load balancer.

DNS
→ gọi Service bằng tên thay vì IP.

Ingress
→ route HTTP/HTTPS từ ngoài vào Service.

Gateway API
→ thế hệ mới, mạnh và linh hoạt hơn Ingress.

NetworkPolicy
→ firewall rule cho Pod traffic.

CNI / Network Plugin
→ thành phần thực thi network thật bên dưới.
```

Một câu tổng kết:

> Networking trong Kubernetes giúp các Pod giao tiếp trực tiếp với nhau, giúp ứng dụng có endpoint ổn định thông qua Service, giúp truy cập từ bên ngoài qua LoadBalancer/Ingress/Gateway API, và giúp kiểm soát traffic bằng NetworkPolicy.
>
