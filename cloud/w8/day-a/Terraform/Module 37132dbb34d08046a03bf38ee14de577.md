# Module

**Module** là một “khối đóng gói” chứa nhiều Terraform resource dùng chung với nhau. Thay vì viết toàn bộ resource trong một file lớn, ta tách chúng thành các module nhỏ như `vpc`, `ecs`, `rds`, `alb`, `route53`. Terraform gọi đây là cách tạo abstraction để mô tả hạ tầng theo kiến trúc, thay vì chỉ theo từng resource vật lý riêng lẻ.

Ví dụ:

```
terraform-project/
├── environments/
│   └── development/
│       ├── main.tf
│       ├── variables.tf
│       └── outputs.tf
└── modules/
    ├── vpc/
    ├── ecs/
    ├── rds/
    └── route53/
```

Trong đó:

```
environments/development/
```

là **root module**.

Còn:

```
modules/vpc
modules/ecs
modules/rds
```

là **child modules**.

Root module là toàn bộ các file `.tf` trong thư mục nơi bạn chạy `terraform plan` hoặc `terraform apply`. Root module có thể gọi các child module và nối chúng lại bằng cách truyền output của module này thành input của module khác.

## Cấu trúc cơ bản của một module

Một module thường có 3 thành phần chính:

```
modules/vpc/
├── main.tf       # định nghĩa resource
├── variables.tf  # input của module
└── outputs.tf    # output trả ra cho module cha
```

Terraform docs mô tả module tái sử dụng thường gồm **input variables**, **output values**, và **resources**. Input dùng để nhận giá trị từ module gọi nó, output dùng để trả kết quả ra ngoài, còn resource là các object hạ tầng mà module quản lý.

Ví dụ module `vpc`:

```
# modules/vpc/variables.tf
variable "vpc_cidr" {
  type = string
}

# modules/vpc/main.tf
resource "aws_vpc" "main" {
  cidr_block = var.vpc_cidr

  tags = {
    Name = "main-vpc"
  }
}

# modules/vpc/outputs.tf
output "vpc_id" {
  value = aws_vpc.main.id
}
```

Sau đó root module gọi module này:

```
module "vpc" {
  source   = "../../modules/vpc"
  vpc_cidr = "10.0.0.0/16"
}
```

Khi child module có output, parent module có thể truy cập bằng cú pháp:

```
module.<module_name>.<output_name>
```

Ví dụ:

```
module.vpc.vpc_id
```

Terraform docs cũng nêu rõ child module có thể expose resource attribute cho parent module thông qua `output`, và parent module truy cập bằng cú pháp `module.<CHILD_MODULE_NAME>.<OUTPUT_NAME>`.

## `module` block là gì?

`module` block dùng để yêu cầu Terraform tạo các resource được định nghĩa trong một module local hoặc remote.

Cú pháp cơ bản:

```
module "network" {
  source = "../../modules/vpc"

  vpc_cidr = "10.0.0.0/16"
}
```

Trong đó:

```
module "network"
```

`network` là tên local của module trong root module.

```
source = "../../modules/vpc"
```

`source` chỉ ra Terraform lấy code module từ đâu. Source có thể là local path, Terraform Registry, GitHub, Git repository, HTTP URL, v.v. Terraform yêu cầu bạn chạy lại `terraform init` sau khi thay đổi `source`.

Một số argument thường gặp trong `module` block:

```
module "example" {
  source  = "./modules/example"
  version = "1.0.0"

  count    = 2
  for_each = var.items

  providers = {
    aws = aws.us_east_1
  }

  depends_on = [
    aws_iam_role.example
  ]
}
```

Lưu ý: `count` và `for_each` không dùng chung với nhau trong cùng một module block. Terraform docs cũng liệt kê các argument built-in như `source`, `version`, `count`, `for_each`, `providers`, và `depends_on`.

## Composition trong Terraform là gì?

**Module composition** là cách ghép nhiều module nhỏ lại với nhau để tạo thành một hệ thống lớn.

Thay vì để module này tự tạo hết dependency bên trong nó, ta để root module đứng ra điều phối:

```
module "network" {
  source = "../../modules/vpc"

  vpc_cidr = "10.0.0.0/16"
}

module "ecs" {
  source = "../../modules/ecs"

  vpc_id     = module.network.vpc_id
  subnet_ids = module.network.private_subnet_ids
}
```

Ở đây:

```
network module tạo VPC/subnet
ecs module nhận vpc_id và subnet_ids từ network module
root module nối 2 module lại với nhau
```

Terraform gọi đây là **module composition**: dùng nhiều building-block module có thể tái sử dụng, rồi lắp chúng lại trong root module để tạo thành hệ thống lớn hơn. Docs khuyến nghị giữ module tree tương đối phẳng, thường chỉ một tầng child module, thay vì tạo cây module lồng nhau quá sâu.

## Ví dụ dễ hiểu

Giả sử bạn có hệ thống AWS gồm:

```
VPC -> ECS -> ALB -> Route53
```

Bạn có thể chia thành các module:

```
modules/
├── vpc/
├── alb/
├── ecs/
└── route53/
```

Root module sẽ compose chúng:

```
module "vpc" {
  source = "../../modules/vpc"

  vpc_cidr = "10.0.0.0/16"
}

module "alb" {
  source = "../../modules/alb"

  vpc_id     = module.vpc.vpc_id
  subnet_ids = module.vpc.public_subnet_ids
}

module "ecs" {
  source = "../../modules/ecs"

  vpc_id            = module.vpc.vpc_id
  private_subnet_ids = module.vpc.private_subnet_ids
  target_group_arn  = module.alb.target_group_arn
}

module "route53" {
  source = "../../modules/route53"

  domain_name    = "example.com"
  alb_dns_name   = module.alb.dns_name
  alb_zone_id    = module.alb.zone_id
}
```

Ý nghĩa:

```
module.vpc tạo network
module.alb dùng output từ vpc
module.ecs dùng output từ vpc và alb
module.route53 dùng output từ alb
```

Đây chính là **composition**.

## Vì sao không nên để module tự tạo dependency bên trong?

Ví dụ module `ecs` tự tạo luôn VPC bên trong:

```
modules/ecs/
├── tạo VPC
├── tạo subnet
├── tạo ECS cluster
└── tạo ECS service
```

Cách này nhìn có vẻ tiện, nhưng về lâu dài sẽ khó tái sử dụng. Nếu bạn muốn nhiều service cùng dùng chung một VPC thì module `ecs` kiểu này không linh hoạt.

Cách tốt hơn:

```
module vpc tạo network
module ecs chỉ nhận vpc_id, subnet_ids
root module quyết định nối chúng như thế nào
```

Terraform docs gọi hướng này là **Dependency Inversion**: module nên nhận dependency từ bên ngoài thay vì tự tạo dependency bên trong, giúp các module có thể được kết nối theo nhiều cách khác nhau.

## Provider trong module

Provider configuration nên được định nghĩa ở **root module**, không nên đặt `provider` block trực tiếp trong reusable child module. Terraform docs nói provider configuration có tính global trong một Terraform configuration, có thể được chia sẻ qua module boundary, và chỉ có thể được định nghĩa trong root module.

Ví dụ root module:

```
provider "aws" {
  region = "ap-southeast-1"
}

provider "aws" {
  alias  = "us_east_1"
  region = "us-east-1"
}
```

Truyền provider alias vào child module:

```
module "cloudfront" {
  source = "../../modules/cloudfront"

  providers = {
    aws = aws.us_east_1
  }
}
```

Child module vẫn nên khai báo `required_providers`:

```
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = ">= 5.0"
    }
  }
}
```

Nhưng không nên tự viết:

```
provider "aws" {
  region = "..."
}
```

bên trong reusable module.

## Khi nào nên tạo module?

Nên tạo module khi một nhóm resource đại diện cho một khái niệm kiến trúc rõ ràng.

Nên:

```
vpc module
ecs_service module
rds module
alb module
route53 module
iam_role_for_ecs module
```

Không nên lạm dụng module cho những wrapper quá mỏng, ví dụ chỉ bọc đúng một resource `aws_s3_bucket` mà không tạo thêm abstraction nào có ý nghĩa. Terraform docs cũng khuyến nghị không nên tạo module chỉ là thin wrapper quanh một resource type duy nhất, vì có thể làm cấu hình phức tạp hơn không cần thiết.

## Tóm tắt ngắn gọn

| Khái niệm | Ý nghĩa |
| --- | --- |
| Root module | Thư mục Terraform chính nơi chạy `plan/apply` |
| Child module | Module được gọi từ root module hoặc module khác |
| Input variable | Giá trị truyền vào module |
| Output value | Giá trị module trả ra ngoài |
| Module block | Cú pháp để gọi module |
| Source | Vị trí code module: local, registry, Git, v.v. |
| Composition | Ghép nhiều module nhỏ lại thành hệ thống lớn |
| Flat composition | Root module điều phối các child module, tránh lồng module quá sâu |

Cách hiểu đơn giản nhất:

```
Module = khối tái sử dụng
Composition = cách ghép nhiều module lại với nhau
Root module = nơi điều phối
Input = dữ liệu đi vào module
Output = dữ liệu đi ra khỏi module
```

Ví dụ thực tế:

```
VPC module output vpc_id
ECS module input vpc_id
Root module nối VPC output vào ECS input
```

Đó là tư duy cốt lõi của **modules and composition trong Terraform**.
