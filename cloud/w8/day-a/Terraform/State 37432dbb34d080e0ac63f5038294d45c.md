# State

**Terraform state** là “bộ nhớ” của Terraform, thường nằm trong file `terraform.tfstate`. Nó lưu thông tin Terraform biết về hạ tầng đã tạo, ví dụ: resource nào đã được tạo, ID thật trên cloud là gì, thuộc tính hiện tại ra sao, output là gì.

Theo tài liệu chính thức, mục đích chính của Terraform state là **lưu mapping giữa resource trong file `.tf` và object thật ngoài hệ thống cloud/provider**. Ví dụ `aws_instance.web` trong code Terraform đang tương ứng với EC2 instance ID nào trên AWS.

## Ví dụ dễ hiểu

Bạn viết:

```
resource "aws_s3_bucket" "demo" {
  bucket = "my-demo-bucket"
}
```

Sau khi chạy:

```
terraform apply
```

Terraform tạo bucket thật trên AWS, sau đó ghi vào state kiểu như:

```
{
  "resources": [
    {
      "type":"aws_s3_bucket",
      "name":"demo",
      "instances": [
        {
          "attributes": {
            "bucket":"my-demo-bucket",
            "id":"my-demo-bucket"
          }
        }
      ]
    }
  ]
}
```

Nhờ đó lần sau khi chạy `terraform plan`, Terraform biết:

> À, `aws_s3_bucket.demo` trong code này chính là bucket `my-demo-bucket` trên AWS.
> 

## Terraform dùng state để làm gì?

### 1. Biết resource nào đang được quản lý

Terraform không chỉ nhìn file `.tf`. Nó còn cần state để biết resource trong code đang ánh xạ với resource thật nào.

Nếu không có state, Terraform có thể không biết resource đã tồn tại và có thể muốn tạo lại resource mới.

### 2. So sánh config với hạ tầng thật

Khi chạy:

```
terraform plan
```

Terraform thường so sánh 3 thứ:

```
Terraform configuration (.tf)
        vs
Terraform state
        vs
Real infrastructure trên cloud
```

Ví dụ bạn đổi:

```
instance_type = "t3.micro"
```

thành:

```
instance_type = "t3.small"
```

Terraform dựa vào state để biết EC2 nào cần update.

### 3. Phát hiện drift

**Drift** là khi hạ tầng thật bị thay đổi ngoài Terraform.

Ví dụ:

- Terraform tạo EC2 `t3.micro`.
- Ai đó vào AWS Console đổi thành `t3.small`.
- Lần sau chạy `terraform plan`, Terraform có thể phát hiện hạ tầng thật đã lệch so với state/config.

### 4. Tăng hiệu năng

Nếu không có state, Terraform sẽ phải query rất nhiều thông tin từ provider mỗi lần chạy. State giúp Terraform có “ảnh chụp gần nhất” của hạ tầng để xử lý nhanh hơn.

## State được lưu ở đâu?

Có 2 kiểu phổ biến:

### 1. Local state

Mặc định, Terraform lưu state ở local:

```
terraform.tfstate
```

Ví dụ thư mục project:

```
main.tf
variables.tf
outputs.tf
terraform.tfstate
```

Cách này phù hợp khi học hoặc làm demo cá nhân.

Nhược điểm:

- Dễ mất file.
- Khó làm việc nhóm.
- Dễ conflict nếu nhiều người cùng chạy Terraform.
- Có thể chứa thông tin nhạy cảm.

### 2. Remote state

Trong thực tế nên dùng **remote backend**, ví dụ:

- AWS S3
- Terraform Cloud / HCP Terraform
- Azure Storage Account
- Google Cloud Storage

Ví dụ backend S3:

```
terraform {
  backend "s3" {
    bucket       = "my-terraform-state-bucket"
    key          = "dev/terraform.tfstate"
    region       = "ap-southeast-1"
    encrypt      = true
    use_lockfile = true
  }
}
```

Backend có nhiệm vụ lưu state và có thể hỗ trợ locking. Tài liệu Terraform nói backend chịu trách nhiệm lưu state và cung cấp API cho state locking nếu backend hỗ trợ.

## State locking là gì?

**State locking** là cơ chế khóa state khi có một process đang ghi state.

Ví dụ:

- User A đang chạy `terraform apply`.
- User B cũng chạy `terraform apply` cùng lúc.
- Nếu không lock, state có thể bị ghi đè hoặc corrupt.
- Nếu có lock, User B phải chờ User A xong.

Terraform sẽ tự lock state cho các thao tác có thể ghi state nếu backend hỗ trợ. Nếu lock thất bại, Terraform sẽ không tiếp tục để tránh làm hỏng state.

## State có chứa secret không?

Có thể có.

Ví dụ state có thể chứa:

- Password RDS
- Secret value
- Access key
- Token
- Connection string
- Output nhạy cảm

Kể cả bạn đánh dấu output là:

```
sensitive = true
```

thì Terraform chỉ ẩn khi hiển thị CLI, còn trong state vẫn có thể lưu giá trị thật.

Vì vậy state cần được bảo vệ kỹ:

- Không commit `terraform.tfstate` lên Git.
- Dùng remote backend có encryption.
- Giới hạn IAM permission.
- Bật versioning cho S3 bucket.
- Bật state locking.
- Không để state public.

## Các lệnh Terraform state hay dùng

### Xem resource trong state

```
terraform state list
```

Ví dụ output:

```
aws_vpc.main
aws_subnet.public[0]
aws_instance.web
```

### Xem chi tiết một resource trong state

```
terraform state show aws_instance.web
```

### Xóa resource khỏi state nhưng không xóa resource thật

```
terraform staterm aws_instance.web
```

Lệnh này chỉ làm Terraform “quên” resource đó, không destroy EC2 thật.

### Import resource có sẵn vào state

```
terraform import aws_s3_bucket.demo my-existing-bucket
```

Dùng khi resource đã tồn tại ngoài cloud và bạn muốn Terraform quản lý nó.

### Đổi địa chỉ resource trong state

```
terraform statemv aws_instance.old aws_instance.new
```

Dùng khi refactor code, đổi tên resource nhưng không muốn Terraform destroy rồi tạo lại.

## Một hiểu nhầm phổ biến

Nhiều người nghĩ:

> File `.tf` là source of truth tuyệt đối.
> 

Thực tế đúng hơn là:

```
.tf config = trạng thái mong muốn
state = trạng thái Terraform đang biết
cloud/provider = trạng thái thật
```

Terraform phải dùng cả 3 để quyết định cần create, update, destroy hay không.

## Tóm tắt ngắn gọn

**Terraform state** là file/bản ghi lưu trạng thái hạ tầng mà Terraform đang quản lý. Nó giúp Terraform biết resource trong code tương ứng với resource thật nào, từ đó tính toán thay đổi khi chạy `plan` và `apply`.

Trong thực tế production, không nên dùng local state. Nên dùng remote backend như S3/Terraform Cloud, bật encryption, versioning, locking và giới hạn quyền truy cập.
