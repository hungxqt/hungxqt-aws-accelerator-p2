# Provisioners

**Provisioners** là cơ chế trong Terraform dùng để chạy một số thao tác phụ sau khi resource được tạo, ví dụ: chạy command, chạy script, copy file cấu hình lên server, hoặc thực hiện thao tác dọn dẹp trước khi destroy resource. HashiCorp mô tả provisioners là cách để “upload files, run commands and scripts” nhằm chuẩn bị resource sau khi Terraform tạo ra nó.

Tuy nhiên, cần nhớ một ý rất quan trọng: **provisioners không phải là cách được khuyến nghị cho hầu hết trường hợp**. Terraform được thiết kế chủ yếu cho mô hình **immutable infrastructure**, nên HashiCorp khuyến nghị dùng các giải pháp chuyên dụng hơn như cloud-init, user data, image baking, configuration management, hoặc tính năng native của provider trước khi dùng provisioners.

### Hiểu đơn giản

Terraform giỏi ở việc:

```
Tạo resource → quản lý state → so sánh drift → plan/apply thay đổi
```

Provisioner thì dùng cho việc kiểu:

```
Sau khi tạo EC2 xong → SSH vào máy → chạy script cài nginx
Sau khi tạo VM xong → copy file config vào máy
Sau khi resource bị xóa → chạy command cleanup
```

Ví dụ:

```
resource "aws_instance" "web" {
  ami           = "ami-xxxx"
  instance_type = "t2.micro"

  provisioner "local-exec" {
    command = "echo EC2 private IP is ${self.private_ip}"
  }
}
```

Ở ví dụ trên, sau khi EC2 được tạo, Terraform sẽ chạy lệnh `echo` trên **máy đang chạy Terraform**, không phải trên EC2.

## Các loại provisioner chính

Terraform có 3 provisioner built-in chính: `file`, `local-exec`, và `remote-exec`.

| Provisioner | Chạy ở đâu? | Dùng để làm gì? |
| --- | --- | --- |
| `file` | Từ máy chạy Terraform đến remote resource | Copy file hoặc thư mục lên server |
| `local-exec` | Máy đang chạy Terraform | Chạy command local |
| `remote-exec` | Máy remote, ví dụ EC2 | SSH/WinRM vào server và chạy command/script |

### `local-exec`

`local-exec` chạy command trên **máy đang chạy Terraform**, ví dụ laptop cá nhân, CI/CD runner, hoặc Terraform runner.

Ví dụ:

```hcl
resource "aws_instance" "web" {
  ami           = "ami-xxxx"
  instance_type = "t2.micro"

  provisioner "local-exec" {
    command = "echo ${self.public_ip} >> instance_ip.txt"
  }
}
```

Dùng khi bạn muốn thực hiện thao tác local, ví dụ ghi IP ra file, gọi một script nội bộ, hoặc gửi thông báo sau khi resource được tạo.

### `remote-exec`

`remote-exec` chạy command trên **remote resource**, thường thông qua SSH hoặc WinRM. Terraform yêu cầu có `connection` block để biết cách kết nối đến server.

Ví dụ:

```hcl
resource "aws_instance" "web" {
  ami           = "ami-xxxx"
  instance_type = "t2.micro"
  key_name      = "my-key"

  connection {
    type        = "ssh"
    user        = "ec2-user"
    private_key = file("~/.ssh/my-key.pem")
    host        = self.public_ip
  }

  provisioner "remote-exec" {
    inline = [
      "sudo yum update -y",
      "sudo yum install -y nginx",
      "sudo systemctl enable nginx",
      "sudo systemctl start nginx"
    ]
  }
}
```

Ở đây, Terraform sẽ SSH vào EC2 rồi chạy các command trong `inline`.

### `file`

`file` dùng để copy file hoặc thư mục từ máy chạy Terraform lên remote resource.

Ví dụ:

```hcl
resource "aws_instance" "web" {
  ami           = "ami-xxxx"
  instance_type = "t2.micro"

  connection {
    type        = "ssh"
    user        = "ec2-user"
    private_key = file("~/.ssh/my-key.pem")
    host        = self.public_ip
  }

  provisioner "file" {
    source      = "app.conf"
    destination = "/tmp/app.conf"
  }
}
```

Thường `file` sẽ đi kèm `remote-exec`, ví dụ copy script lên server rồi chạy script đó.

### `connection` block là gì?

`connection` block khai báo cách Terraform kết nối tới remote resource. Nó thường dùng cho `file` và `remote-exec`.

Ví dụ:

```hcl
connection {
  type        = "ssh"
  user        = "ec2-user"
  private_key = file("~/.ssh/my-key.pem")
  host        = self.public_ip
}
```

Terraform hỗ trợ kết nối qua SSH hoặc WinRM. `connection` có thể đặt ở cấp `resource` để dùng chung cho nhiều provisioner, hoặc đặt riêng trong từng `provisioner`.

## Creation-time provisioner

Mặc định, provisioner chạy **sau khi resource được tạo**.

Ví dụ:

```
resource "aws_instance" "web" {
  # ...

  provisioner "local-exec" {
    command = "echo created"
  }
}
```

Nếu creation-time provisioner bị lỗi, Terraform sẽ đánh dấu resource là **tainted**, vì resource có thể đang ở trạng thái cấu hình dở dang. Lần `terraform apply` tiếp theo, Terraform có thể destroy và tạo lại resource đó.

## Destroy-time provisioner

Destroy-time provisioner chạy **trước khi resource bị destroy**.

Ví dụ:

```
resource "aws_instance" "web" {
  # ...

  provisioner "local-exec" {
    when    = destroy
    command = "echo destroying instance"
  }
}
```

Destroy-time provisioner dùng `when = destroy`. HashiCorp lưu ý rằng nếu destroy provisioner thất bại, Terraform sẽ báo lỗi và có thể chạy lại provisioner ở lần apply tiếp theo, nên logic cleanup cần an toàn khi chạy nhiều lần.

## `on_failure`

Mặc định, nếu provisioner lỗi thì `terraform apply` cũng lỗi. Có thể đổi hành vi bằng `on_failure = continue`.

Ví dụ:

```
resource "aws_instance" "web" {
  # ...

  provisioner "local-exec" {
    command    = "echo ${self.private_ip}"
    on_failure = continue
  }
}
```

Khi dùng `continue`, Terraform sẽ bỏ qua lỗi của provisioner và tiếp tục apply.

## Dùng `self` thay vì tên resource

Trong `provisioner` hoặc `connection`, không nên tham chiếu resource cha bằng tên trực tiếp. Thay vào đó dùng `self`.

Đúng:

```
command = "echo ${self.private_ip}"
```

Không nên:

```
command = "echo ${aws_instance.web.private_ip}"
```

Terraform yêu cầu dùng `self` trong trường hợp này để tránh vòng lặp dependency bên trong chính resource đó.

## Vì sao nên hạn chế dùng provisioners?

Provisioners có vẻ tiện, nhưng có nhiều vấn đề:

1. **Terraform khó dự đoán được kết quả của script/command**
Terraform quản lý state của resource, nhưng không hiểu sâu bên trong script bạn chạy đã thay đổi gì.
2. **Dễ làm infrastructure không còn idempotent (bất khả kháng)**
Nếu script chạy nhiều lần mà không được viết cẩn thận, kết quả có thể khác nhau.
3. **Cần SSH/WinRM vào server**
Điều này làm tăng độ phức tạp về network, security group, key pair, credentials, bastion host.
4. **Dễ gây lỗi khi chạy trong CI/CD**
Ví dụ máy CI/CD không có SSH key, không reach được private subnet, hoặc command local khác nhau giữa Windows/Linux.
5. **Không phù hợp với immutable infrastructure**
Thay vì tạo server rồi SSH vào cài app, cách tốt hơn là build sẵn AMI/image hoặc dùng user data/cloud-init.

HashiCorp cũng khuyến nghị nên dùng provisioners như phương án cuối cùng, sau khi đã xem xét các giải pháp khác.

## Nên dùng gì thay provisioners?

Tùy trường hợp:

| Nhu cầu | Nên dùng |
| --- | --- |
| Cài package khi EC2 boot | `user_data`, cloud-init |
| Build server image chuẩn | Packer |
| Cấu hình server sau khi tạo | Ansible, Chef, Puppet |
| Chạy container | ECS, EKS, Docker image |
| Truyền config cho app | SSM Parameter Store, Secrets Manager, environment variables |
| Gọi API sau khi apply | Provider native resource hoặc Terraform action/invoke nếu phù hợp |
| Copy file cấu hình | AMI/image, S3, user data, config management |

## Ví dụ thực tế: cài nginx bằng provisioner

Cách này chạy được, nhưng không phải best practice:

```
resource "aws_instance" "web" {
  ami           = "ami-xxxx"
  instance_type = "t2.micro"
  key_name      = "my-key"

  connection {
    type        = "ssh"
    user        = "ec2-user"
    private_key = file("~/.ssh/my-key.pem")
    host        = self.public_ip
  }

  provisioner "remote-exec" {
    inline = [
      "sudo yum install -y nginx",
      "sudo systemctl enable nginx",
      "sudo systemctl start nginx"
    ]
  }
}
```

Cách tốt hơn thường là dùng `user_data`:

```
resource "aws_instance" "web" {
  ami           = "ami-xxxx"
  instance_type = "t2.micro"

  user_data = <<-EOF
              #!/bin/bash
              yum install -y nginx
              systemctl enable nginx
              systemctl start nginx
              EOF
}
```

Với AWS EC2, `user_data` thường hợp lý hơn vì script chạy ngay khi instance boot, không cần Terraform SSH vào server.

## Tóm tắt dễ nhớ

**Provisioners = chạy hành động phụ sau khi Terraform tạo hoặc trước khi Terraform xóa resource.**

Có 3 loại chính:

```
local-exec  → chạy command trên máy chạy Terraform
remote-exec → SSH/WinRM vào remote server để chạy command
file        → copy file/thư mục lên remote server
```

Nhưng về best practice:

```
Không nên lạm dụng provisioners.
Chỉ dùng khi không còn cách tốt hơn.
Ưu tiên user_data, cloud-init, Packer, Ansible, provider-native features.
```

Một câu ngắn gọn để ghi chú:

> Provisioners trong Terraform dùng để thực hiện các thao tác như chạy command/script hoặc copy file sau khi resource được tạo hoặc trước khi resource bị destroy. Tuy nhiên, vì Terraform không thể mô hình hóa chính xác các thay đổi do script gây ra, provisioners nên được xem là giải pháp cuối cùng, không phải best practice chính.
